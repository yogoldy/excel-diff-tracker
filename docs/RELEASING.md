# Releasing

Release promotion is deliberately a build-once process. GitHub Actions can produce an unpromoted candidate for comparison, but it does not publish a different, untested installer.

1. Begin from a clean committed checkout on Windows 11 ARM64 and run `scripts\build-release.ps1 -Version X.Y.Z`. The script records that 40-character build-source commit and an exact SHA-256 manifest of every tracked file except the generated WinGet installer-hash manifest inside the installed package. It then builds, tests, publishes the self-contained app, bundles exact third-party runtime notices, compiles the installer, writes checksums, and updates the matching WinGet manifest hash.
2. Commit only the generated WinGet installer-hash change. This creates the release commit. The embedded build-source commit must be its ancestor, and their only changed path must be that version's WinGet installer manifest. Record both commits, the installer SHA-256, and the name/ID of the clean VM snapshot used for each run. Any other post-build change requires a rebuild.
3. Test that exact `artifacts\release\ExcelDiffTracker-Setup-arm64.exe` on Windows 11 ARM64 using `scripts\acceptance\Invoke-BlackBoxAcceptance.ps1`. Pass the embedded build-source commit through `-ExpectedSourceCommit`, plus the frozen installer hash and snapshot identity with `-ExpectedInstallerSha256`, `-VmSnapshotName`, `-VmSnapshotId`, and `-ConfirmCleanSnapshot`. The harness independently matches the installed build identity/source manifest to the clean release checkout and records both commits. Each run automatically includes the long-lock gate, full installed recovery matrix, dual-format semantic matrix, installed 500,000-cell benchmark, and ten-minute/20-save real-Excel soak. Supporting smokes do not replace the two installed-product runs, visual matrix, and independent attestations.
4. On a fresh disposable VM, run the two-phase [installed lifecycle and in-place-upgrade gate](INSTALLED_LIFECYCLE_UPGRADE.md) with the retained prior public installer and the exact candidate. Phase 1 must install and exercise the actual prior version, upgrade it in place, and stop pending an external Windows logoff. After a real logoff/sign-in, phase 2 must prove quiet startup from the new interactive logon, preserved history, tray behavior, uninstall cleanup, and retained local history. A same-version repair, process restart, lock/unlock, or simulated `--background` launch does not satisfy this gate.
5. Run `scripts\acceptance\Test-AcceptanceEvidence.ps1` against the complete evidence directory, exact current and prior installers, their independently frozen installed-application hashes and versions, exact published acceptance probe, and the same genuine macro-enabled fixture supplied through `-XlsmFixture`. Supply an explicit zero-offset `-AcceptanceCutoffUtc` from immediately before the first clean run. The validator rejects cutoffs over 30 days old, runs predating the cutoff, reused outer/subgate evidence IDs, identical run manifests, and reordered/out-of-run timestamps. It also requires the retained prior installer/application/version to match `packaging/release-baselines.json`, which pins the actual public prior release. `approval.json` is written only when all identities, both runs, mandatory product gates, the exact lifecycle/upgrade result, both installed semantic matrices, required visual configurations, and all attestations agree.
6. Make no repository changes after acceptance. The candidate commit from step 2 must already contain the final WinGet hash; if any source, packaging, metadata, or installer byte changes, discard the evidence and restart acceptance.
7. From an authenticated checkout, run `scripts\publish-tested-release.ps1 -AcceptanceDirectory <evidence-directory> -XlsmFixture <tested-macro-fixture> -PriorInstallerPath <prior-installer> -ExpectedPriorApplicationSha256 <pinned-prior-installed-exe-sha256> -PriorVersion <prior-version> -AcceptanceCutoffUtc <same-zero-offset-cutoff>`. It reruns aggregate acceptance with `-Version` as the candidate version and refuses to publish if lifecycle/upgrade evidence is absent, attestation bytes changed, the release commit/build manifest is inconsistent, the tree is dirty, the installer/checksums/WinGet manifest disagree, or `approval.json` does not approve the exact installer. It creates and pushes the version tag, then uploads the exact tested files.
8. Validate and install the published WinGet manifest locally. Submit it to `microsoft/winget-pkgs` only after the release URL is live and all required validation passes.

The first unsigned release should be promoted with `-Prerelease` until onboarding, tray interaction, themes, high contrast, keyboard navigation, and scaling have been manually accepted.
